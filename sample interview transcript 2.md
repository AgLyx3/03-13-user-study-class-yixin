# User Interview Transcript 2

---

**Interviewer:** Thanks for being here. Can you tell me about the last group project you worked on?

**Student:** Yeah, it was for a design course. We had to build and test a prototype, then write everything up. Engineering group projects are weird because the work sounds very divisible. Like one person CADs something, one person runs analysis, one person writes, one person presents. So at first it feels manageable.

**Interviewer:** And did it feel manageable?

**Student:** At first, yes. In reality the dependencies are annoying. Like you can't finish the report if testing isn't done, and you can't finish testing if the model changed, and then someone is waiting on someone else. So the actual issue is less "who has a task" and more "do we all know the state of the project."

**Interviewer:** How did you keep track of that state?

**Student:** Badly. Sorry. Mostly through text and some Google Docs comments. Sometimes email if one person is more formal than the rest of the group.

**Interviewer:** What happened in the last project specifically?

**Student:** We had one in-person planning meeting, and everybody left feeling like we had a plan. Which I think is common. People confuse a good meeting with actual coordination.

**Interviewer:** That's a good line. What do you mean by that?

**Student:** Just that after the meeting, there wasn't really one place that said: this is the latest plan, these things changed, this part is blocked. We had fragments of that in different places.

**Interviewer:** Was there a group chat?

**Student:** Yeah, there is always a group chat. For this one it was just iMessage. But then one person preferred email, so sometimes important stuff happened there too, which was even worse.

**Interviewer:** Worse because it was split across channels?

**Student:** Yeah. Also because people assume communication happened if they sent it somewhere. Not if the group actually absorbed it.

**Interviewer:** Can you think of a moment where that caused a problem?

**Student:** Yeah. One person updated the dimensions on a part after testing, and they mentioned it in the chat. But the person writing the report didn't see it and used the old numbers. We didn't catch that until pretty late.

**Interviewer:** So version control was the issue?

**Student:** Sort of. But I think if I just call it version control it sounds more technical than it felt. The actual feeling was: nobody knows which update matters and who still needs to react to it.

**Interviewer:** That's useful. What did you do once you realized that?

**Student:** I texted the person I thought was most responsible, which is honestly what happens a lot. Not because it's a great system, but because when things get messy people stop relying on the group and start relying on whoever seems most on top of it.

**Interviewer:** Is there usually one person carrying the coordination?

**Student:** Kind of. Not officially. But one person usually becomes the human reminder system.

**Interviewer:** How do they become that person?

**Student:** Either they're the most organized, or they're the most anxious. Sometimes both.

**Interviewer:** That's real.

**Student:** Yeah.

**Interviewer:** Did anyone try a project management tool?

**Student:** We tried Trello in a different class. It looked nice for like three days. Then it got stale.

**Interviewer:** Because nobody updated it?

**Student:** Yeah, and because the real conversation still happened elsewhere. So the board became like a fake layer on top of reality. People stopped trusting it pretty fast.

**Interviewer:** When you say "reality," do you mean the chat?

**Student:** The chat, side conversations, comments in documents, people talking before class. That's part of why this is hard. The coordination is kind of everywhere.

**Interviewer:** If you had a tool, would you want it to replace the chat?

**Student:** No, probably not. I don't think students are going to leave the chat. If anything, it should make the chat less chaotic.

**Interviewer:** What would "less chaotic" mean to you?

**Student:** Being able to tell, quickly, what decisions have been made, what changed, and who still needs something from me. Also deadlines, obviously.

**Interviewer:** So maybe like task assignment plus reminders?

**Student:** Maybe, but I wouldn't start with reminders. Everyone already has too many reminders. I think clarity comes first.

**Interviewer:** That's interesting. I was focusing on reminders because you mentioned deadlines.

**Student:** Deadlines matter, but the worse feeling is not knowing whether you're blocked, or whether someone else is waiting on you and you don't realize it.

**Interviewer:** That sounds more like dependency tracking.

**Student:** Yeah, maybe. I wouldn't call it that as a student, but sure.

**Interviewer:** Fair. If something summarized the chat for you, would that help?

**Student:** It could, if it pulled out the things that matter. Like decisions, ownership, changes. Not just a summary of everything people said.

**Interviewer:** So not "meeting notes," more like "state of the project"?

**Student:** Yes, exactly. That's a much better way to say it.

**Interviewer:** What would make you not trust a tool like that?

**Student:** If it missed a change, or confidently stated something that was outdated. In engineering projects, one outdated detail can mess up a bunch of downstream work.

**Interviewer:** That makes sense. Anything else about these projects that feels important?

**Student:** I think people talk about group projects like the problem is freeloading. Sometimes it is. But honestly a lot of the stress comes from coordination overhead, even when everyone is trying.

**Interviewer:** That's a good place to stop. Thank you.
